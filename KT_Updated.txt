This KT is the single restart/reference guide for the CloudNativeEcommerce project.

It covers:
- .NET microservices
- Docker / Docker Compose
- SQL Server, MongoDB, RabbitMQ
- Serilog + Seq
- Kubernetes
- Helm
- Terraform
- Azure Container Registry (ACR)
- Azure Kubernetes Service (AKS)
- ingress-nginx
- Azure Load Balancer health-probe fix
- rebuilding the whole environment from scratch
- image build/push/deploy flow
- debugging commands
- port-forwarding

> IMPORTANT SECURITY NOTE
> Never store real passwords, JWT keys, Docker tokens, Azure service-principal passwords, or other credentials in this KT.
> Use placeholders such as <SQL_PASSWORD>, <JWT_KEY>, <AZURE_CLIENT_SECRET>.
> If a real credential was previously pasted into a KT, rotate it and remove it from Git/history.

# 3. What Each Major Technology Does

## .NET 8

Runs all application services.

## Docker

Packages each service and its dependencies into repeatable images.

## Docker Compose

Used for local development.

It runs SQL Server, MongoDB, RabbitMQ, Seq and application containers locally.

## Kubernetes

Runs the application in a cluster.

## Deployment

Maintains the desired number of Pods.

Example:

```yaml
replicas: 2
```

## Pod

Runs the actual container.

Pods are disposable.

## Service

Provides stable internal networking.

Examples:

```text
sqlserver
mongodb
rabbitmq
seq
identityservice
productservice
orderservice
apigateway
```

The Pod IP can change; the Service name remains stable.

## ConfigMap

Stores non-sensitive configuration.

Examples:

```text
MongoDB connection string
RabbitMQ host
Seq URL
JWT issuer
JWT audience
```

## Secret

Stores sensitive configuration.

Examples:

```text
SQL password
JWT signing key
connection strings containing passwords
```

## Helm

Packages and deploys Kubernetes resources.

## Terraform

Creates Azure infrastructure.

Current infrastructure:

```text
Resource Group
    |
    +-- ACR
    |
    +-- AKS
```

## ACR

Azure Container Registry stores Docker images.

Example:

```text
cloudnativeecommerceacr67.azurecr.io
```

## AKS

Azure Kubernetes Service runs Kubernetes in Azure.

## ingress-nginx

Provides the external HTTP/HTTPS entry point into the cluster.

# 16. IMPORTANT: Azure Load Balancer Health Probe Issue

This was one of the major issues encountered.

The ingress-nginx Service had:

```yaml
appProtocol: http
```

Azure therefore created an HTTP health probe.

Without the explicit annotation, Azure probed:

```text
/
```

But ingress-nginx returned:

```text
404
```

So Azure considered the backend unhealthy.

Result:

```text
Browser/curl
   |
   v
Azure Load Balancer
   |
   X
No healthy backend
```

Symptoms:

```text
Connection timeout
```

while internal traffic could still work.

The permanent fix is:

```yaml
service.beta.kubernetes.io/azure-load-balancer-health-probe-request-path: /healthz
```

ingress-nginx returns:

```text
/healthz -> 200 OK
```

Therefore Azure sees a healthy backend.

### NEVER manually annotate the Service after this configuration is in place.

Do NOT rely on:

```cmd
kubectl annotate svc ...
```

The Helm values file is the source of truth.

Every future ingress-nginx installation must use:

```cmd
-f ingress-nginx-values.yaml
```

# 23. AKS -> ACR Permission

AKS kubelet identity needs:

```text
AcrPull
```

Terraform configuration:

```hcl
resource "azurerm_role_assignment" "aks_acr_pull" {
  principal_id = azurerm_kubernetes_cluster.aks.kubelet_identity[0].object_id

  role_definition_name = "AcrPull"

  scope = azurerm_container_registry.acr.id
}
```

If Azure says:

```text
RoleAssignmentExists
```

do not create a duplicate assignment.

Check Terraform state:

```cmd
terraform state list
```

If it already contains:

```text
azurerm_role_assignment.aks_acr_pull
```

Terraform is already tracking it.

Then:

```cmd
terraform plan
```

should eventually show no infrastructure changes.

# 27. Terraform Rebuild Warning

Terraform can destroy and recreate AKS when configuration differs from the existing cluster.

A plan showing:

```text
-/+ destroy and then create replacement
```

means replacement.

Always inspect the plan before approving.

A Resource Group deletion can also fail if it contains resources Terraform does not currently manage.

We encountered this with:

```text
Microsoft.KeyVault/vaults/cloudnativeecommercekv67
```

Terraform refused to delete the Resource Group because a resource still existed inside it.

Do NOT blindly disable deletion protection.

First identify the unmanaged resource:

```cmd
az resource list ^
  --resource-group CloudNativeEcommerce-RG ^
  -o table
```

Then decide whether it should be imported, explicitly deleted, or intentionally preserved.

# 28. Full Destroy / Rebuild Procedure

This is the most important section.

If the goal is to completely rebuild the Azure environment:

## Step 1 – Confirm current Terraform state

```cmd
cd terraform
terraform state list
```

```cmd
terraform plan
```

Read the plan carefully.

If it shows unexpected replacement/destruction, stop and inspect.

## Step 2 – Destroy infrastructure

```cmd
terraform destroy
```

Confirm only after reviewing what will be destroyed.

This destroys Terraform-managed Azure infrastructure.

It can remove:

```text
Resource Group
ACR
AKS
AKS node resource group
Kubernetes cluster resources
```

It does NOT magically preserve Kubernetes workloads.

If SQL Server, MongoDB, RabbitMQ, Seq and application Pods are running inside AKS, they disappear when AKS is destroyed.

For this project, those are recreated from Helm after AKS is recreated.

## Step 3 – Recreate Azure infrastructure

```cmd
terraform apply
```

Verify:

```cmd
terraform output
```

Expected:

```text

aks_name
aks_resource_group
resource_group_name
```

# 36. Important Lessons From Problems We Encountered

## Problem 1 – Docker build could not find .csproj

Error:

```text
/src/ApiGateway/ApiGateway.csproj: not found
```

Cause:

Dockerfile expected:

```text
src/ApiGateway/ApiGateway.csproj
```

Therefore the Docker build context must be the repository root.

Correct pattern:

```cmd
docker build -t <image> ^
  -f src\ApiGateway\Dockerfile .
```

The final `.` is important.

---

## Problem 2 – ImagePullBackOff

Cause:

AKS could not pull images from ACR.

Fix:

- images must exist in ACR
- AKS kubelet identity needs `AcrPull`
- use correct image names
- restart Deployment after pushing `latest`

---

## Problem 3 – Terraform wanted to replace AKS

Plan showed:

```text
-/+ destroy and then create replacement
```

Cause:

Terraform configuration did not exactly match the existing AKS configuration.

Lesson:

Always inspect:

```cmd
terraform plan
```

before:

```cmd
terraform apply
```

---

## Problem 4 – Resource Group would not delete

Terraform reported:

```text
Resource Group still contains Resources
```

because a Key Vault existed that Terraform was not managing.

Lesson:

Before destroying a Resource Group:

```cmd
az resource list ^
  --resource-group CloudNativeEcommerce-RG ^
  -o table
```

Check for resources outside Terraform state.

---

## Problem 5 – Public IP changed after rebuild

Old IP:

```text
<OLD_IP>
```

New cluster:

```text
<NEW_IP>
```

Lesson:

Never hard-code Azure public IPs in the KT.

Always retrieve the new IP:

```cmd
kubectl get svc -n ingress-nginx
```

or Azure CLI.

Then update hosts.

---

## Problem 6 – cloudnative.local stopped resolving

Cause:

Hosts/DNS still pointed at an old IP.

Fix:

Update:

```text
C:\Windows\System32\drivers\etc\hosts
```

with:

```text
<NEW_PUBLIC_IP> cloudnative.local
```

---

## Problem 7 – External API timed out even though internal traffic worked

Root cause:

Azure Load Balancer HTTP health probe was hitting:

```text
/
```

ingress-nginx returned:

```text
404
```

Azure therefore marked the backend unhealthy.

Permanent fix:

```yaml
service.beta.kubernetes.io/azure-load-balancer-health-probe-request-path: /healthz
```

This is now stored in:

```text
ingress-nginx-values.yaml
```

and must always be passed to Helm.

---

## Problem 8 – Testing with an old Node IP

A previous test used a node IP that belonged to the old cluster.

Lesson:

Do not assume:

```text
10.224.x.x
```

is still valid.

Get the current node IP:

```cmd
kubectl get nodes -o wide
```

Prefer Service DNS instead:

```text
http://ingress-nginx-controller.ingress-nginx.svc.cluster.local/healthz
```

---

## Problem 9 – `az acr login` failed because Docker Desktop was unavailable

Error:

```text
DOCKER_COMMAND_ERROR
```

Cause:

Docker Desktop's Linux engine was not running.

Fix:

Start Docker Desktop and retry:

```cmd
az acr login --name cloudnativeecommerceacr67
```

---

## Problem 10 – Helm transient HTTP/2 error

Error:

```text
http2: client connection lost
```

Cause:

Transient connection problem while Helm queried the cluster/release.

Fix:

Retry the Helm command before changing configuration.

# 40. Golden Rules

1. Always run `terraform plan` before `terraform apply` when infrastructure changes.
2. Never approve an unexpected `-/+ destroy and create replacement`.
3. Never hard-code AKS node IPs.
4. Never hard-code the Azure ingress public IP in documentation.
5. After AKS rebuild, retrieve the new public IP.
6. Always install ingress-nginx with `ingress-nginx-values.yaml`.
7. Never manually annotate the ingress-nginx Service once Helm owns the annotation.
8. Always build Docker images from the repository root.
9. If using `:latest`, use `imagePullPolicy: Always` and restart the Deployment after pushing.
10. Use Kubernetes Service DNS names instead of Pod IPs.
11. Use `kubectl describe` and Events for ImagePullBackOff.
12. Use `kubectl get endpoints` for Service connectivity problems.
13. Port-forwards stop when their terminal closes.
14. Never store real credentials in this KT.
15. Treat Terraform state as the source of truth for Azure resources managed by Terraform.
16. Treat Helm values/templates as the source of truth for Kubernetes resources managed by Helm.
17. If a resource exists in Azure but not Terraform state, investigate before destroying the Resource Group.
18. After a full rebuild, verify nodes → ingress-nginx → ACR/images → application Helm → Pods → Services → Ingress → public IP → hosts file → external curl.
